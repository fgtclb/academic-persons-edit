Every shape the browser rendered editors draw, rendered once per page. The document editor and the contact list cannot be server rendered as finished markup: their fields, labels, options and display values come from the "documentForm" and "contractContactForm" responses, and those endpoints answer field descriptors, never HTML. So Fluid renders the shapes and JavaScript fills them - "Resources/Private/TypeScript/ frontend/profile/prototypes.ts" clones a template and resolves exactly four attributes: data-pe-slot="key" the node's text becomes the value data-pe-attr="attribute:key" those attributes take the value data-pe-when="key" the node is removed when it is falsy data-pe-list="key" where repeated clones go A prototype contains no branching. The only decision this tree makes is which prototype is emitted - the "prototype" flag of Profile/Field/Control.html and the shape argument of Profile/Field/PrototypeWrapper.html - and this file makes none at all. A case that would need a fifth verb is a case that should have been server rendered. Two of them came up while this was written and both were answered here or in CSS rather than in TypeScript: a save button that is red for a delete is two buttons and a "data-pe-when", and the striping of the contact rows is a ":nth-child" rule of "Resources/Private/Scss/frontend/profile-editing.scss". No element and no filler writes markup: every tag, every class attribute and every label of the two editors is authored here. What JavaScript does spell are the *state* classes it toggles on markup that already exists - "d-none", "is-invalid" and the rest - and a few selectors; both are part of the override contract and are listed in Documentation/ProfileEditing/Index.rst. Overriding this partial changes the markup of both editors. What an override cannot change is the order the elements insert things in and which slot carries which value - those are TypeScript.
